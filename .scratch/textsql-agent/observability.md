# 可观察性：怎么判「这条 SQL 在回答那句话」

这份文件回答一个问题：**跑一句问法，怎么用硬量判它对不对**。不是"看着像对的"，是数字对得上。

配套：`spec.md` 的唯一测试缝（一轮）、`flow-design.md` 第九节（待定项）、
`docs/adr/0002`（自由文本摘要 + 业务词不进 `src/`）。

---

## 一、可观察量长在 B 环内，不外挂

外挂审计（跑完一轮再从外面重跑 SQL 比对）是错的：那等于在 B 环外另建一条观察通路，
撞「唯一测试缝：一轮」。**每一跳的可观察量必须由 B 环自己产出，经 `QueryToolOutcome`
→ `TurnResult` 出来。**

| 层 | B 环位置 | 可观察量 | 软硬 |
|---|---|---|---|
| B2 主 Agent | `planner.py` | `query_tool_arguments["当前问题"]` | 软（跟金标那句比，报告不判） |
| B3 改写 | `rewrite.py` | `rewritten_question`、`query_summary` | **软**（改写有没有保住条件，靠人读） |
| B4 检索 | `rag.py` | `rag_hits` 三路各自长度 | 硬（字符串存在性） |
| B5 查库 | `sql_session.py` | `sql_text`、`readonly_returns`、**`matched_rows`** | **硬**（可执行／基数／次数／报错序列） |
| B6 回填 | `query_tool.py` | `entities`、`enrichments`、`enrichment_call_count`、`miss_logged`、材料分段 | 硬（B6.2–B6.5 本轮只占位） |
| 出口 | `turn.py` | `TurnResult` 以上全部 | — |

**不新增测试缝，不新增顶级编号，主 Agent 契约一字不改。**

### 1.1 精确基数：`RowSet.matched_rows`

执行器对每条 SQL 跑两次：

```sql
SELECT COUNT(*) FROM (<去掉尾部 LIMIT 的 SQL>)   -- 精确命中总数
<原SQL>                                          -- 取行，供回填
```

- `COUNT(*)` 包在子查询里，要求原 SQL 是单条 SELECT——这个前提由只读校验保证。
- **必须去掉尾部 LIMIT**，否则 `COUNT(*)` 只数到 LIMIT 那么多。
- 基数与取行上限（`row_limit`）、回填截断（50 行 / 4000 字）**三者互不影响**。

这个量生产本来就需要（回填写「从 23,602 人里取 5 条」这句采样说明只能用基数写），
所以它不是评测专用的外挂。

### 1.2 判据

| 判据 | 怎么算 | 软硬 |
|---|---|---|
| 基数 | 独立通路重数（另开一条只读连接）再比 | 硬 |
| 锚点必含／必不含 | 金标里 ≤5 个 `xhs_id`，在模型 SQL 的**整个结果集**里找，不受回填行数限制 | 硬 |
| 期望分支 | 有行／0行／失败，与 `readonly_returns[-1].kind` 比 | 硬 |
| 名字核对 | SQL 里的表名列名，有几个在材料里找不到 | 硬 |
| 采样说明 | 回填里有没有「命中 N 条，回填 M 条」 | 硬 |
| 改写问题 | 只报原文，不判 | 软 |

锚点抓的是基数看不出的错：粉丝恰好 50,000 的必须在内、50,001 的必须不含。
全量集合 diff 只在归因时才用。

### 1.3 归因（按需，不一开始就上）

先看基数对不对。对不上时，把**金标 SQL 的 WHERE 按顶层 AND 拆开**，生成 2^k 个条件子集变体
（只留部分条件的 AND 组合）各数一遍，取最接近模型那个数的变体 → 直接报「模型少了哪个条件」。

不引入 sqlglot：同一语义有多种写法，AST 比对会假阴性；变体格报的是人话。

## 二、怎么用

```bash
cd .scratch/textsql-agent/tools

# 判据本身对不对：退化解校准，不调模型、不需要 key
uv run --with pyyaml --python 3.12 python run_eval.py xhs_pgy.sqlite3 --self-test

# 写问法之前体检一句：每一跳 + 类目对账 + 已知坑
uv run --with pyyaml --python 3.12 python check_question.py xhs_pgy.sqlite3 "一句问法"

# 跑金标
uv run --with pyyaml --python 3.12 python run_eval.py xhs_pgy.sqlite3
uv run --with pyyaml --python 3.12 python run_eval.py xhs_pgy.sqlite3 --backfill   # 回填 `基数`
```

三个脚本都在 `.scratch/textsql-agent/tools/`，都只读（`--backfill` 只写 `config/blogger.yml`）。
真组件一个不换：真 DeepSeek、真只读执行器、真库。要 3.12（`src/` 用了 `zip(strict=)`）。

### 2.1 自检（退化解）

判据不对，真问法的判定就没意义。所以先用退化 SQL 校准判据：

| 退化解 | 校准什么 | 实测 |
|---|---|---|
| 全表 `WHERE xhs_id IS NOT NULL` | 比对器不误报 | 470,345 ✓ |
| 同一语义另一种写法（改列顺序 + `ORDER BY`） | 判据不靠 SQL 字面 | 470,345 vs 470,345 ✓ |
| 故意丢一个条件 | 变体格归因报出丢了哪个条件 | 报出少了 `email IS NOT NULL` ✓ |
| 故意取补集（`xhs_id IS NULL`） | 召回低时报得出方向 | 54 = 470,399 − 470,345 ✓ |

退化解明确标在 `run_eval.py` 顶部的注释里，**绝不长得像真实问法**。
前科在这儿：为可观察编的销售示踪弹被当成了真实库结构。

### 2.2 金标（`textsql-agent/config/`）

| 文件 | 是什么 |
|---|---|
| `blogger.yml` | 金标：问法／金标SQL／基数／锚点／条件清单。**问法由人填，脚本不编** |
| `blogger_ddl.sql` | 进 B4 表结构那一路的材料 |
| `blogger_docs.md` | 进 B4 文档那一路的材料：114 个类目名 + 分位数 + 已知脏值 |

一份数据三个用途：B4 的问题-SQL 样例材料、评测标准答案、类目同义词映射的落点。

**金标过期**是独立判定：`锚点.行数` 或某条的 `基数` 与库对不上，就报过期，
这一条不参与判定——不然分不清「模型查错了」和「金标记错了」。

### 2.3 打码分两层（脚本 stdout 是日志，产品形态才给明文）

| 层 | 打什么 | 用在哪 |
|---|---|---|
| `mask_email` | 只打邮箱 → `a***@domain`，数字原样 | **自由文本行**：回复／SQL／当前问题／改写问题／需求说明／回填头 |
| `mask` | 邮箱 + 长数字（前 3 后 2） | **逐行数据的行**：回填行 |

自由文本行不打长数字，两个理由：START-HERE 的规则里有一条「**聚合统计不打码**」；
而且 SQL 里的阈值被打成 `100**00` 就没法读了，这工具就白做。
另外 `xhs_id` 是混合字母数字（`00000100000` 全数字、`0000000000ly` 带字母），
长数字那层本来就只挡得住全数字那批——带字母的挡不住，那是执行器列投影的事。
昵称一律保留原文。

这里踩过三次，都记下来：

1. 第一版 `render()` 只对回填打了码，**「回复」那一行是裸的**，而模型会把行数据回显进回复，
   于是真邮箱直接进了 stdout；`check_question.py` 和 `run_eval.py` 都经 `render()`，两个都漏。
   凡是新增 `render()` 的行，先问一句「这行可能带邮箱吗」。
2. 补完上面那处之后，**下一层还漏**：`EMAIL` 正则原来只在「空白 `@` `|`」处停，
   于是 `email IN ('a@x.com','b@y.com')` 里两个邮箱只隔一个引号加逗号，
   第二个被吞进第一个匹配，本地部分原样输出。**模型写的 `IN (...)` 列表几乎不带空格**，
   所以这是现实可达的。当时的修法是给边界字符类补中英文标点和括号。
3. **补边界是补不完的**——第 2 条的修法仍然是反面枚举「哪些字符算分隔符」，
   实测补到第 21 个还有漏的：`alice@x.com/bob@y.com` → `a***@x.com/bob@y.com`
   （`/ \ & # ! ? * ^ = ~ \` $ · — … •` 逐个都漏）。真正的修法是**正面定义**：
   正则从「邮箱里允许出现的字符」出发（`_EMAIL_CHARS`），凡是邮箱里不可能出现的字符
   天然断开这一段，不用一个个列。剩下的 `-` `.` `+` `_` `%` 是合法邮箱字符，
   按字符类切不开「两个邮箱只隔一个 `-`」这种写法——那就**整段吞下来一起打**：
   一个匹配里所有 `@` 前面的本地部分都只留首字符，退化情形下多打几个字符，但一个不漏。

判据是「有没有漏」，不是「看起来对不对」——三次都是拿**真实 SQL 字面量**试出来的，
不是读代码看出来的。改打码之后，至少要用 `IN ('a@x','b@y')`、`a@x,b@y`、全角逗号
这三种无空格写法各试一遍；**再补一轮 48 个分隔符的扫描**
（`alice@x.com<sep>bob@y.com`，逐个看 `bob` 还在不在），
因为第 3 条正是「只试了那三种、以为修完了」才漏过去的。

**全角 at 号（已修，2026-09-17）**

`alice＠x.com`（全角 `＠`，U+FF20）原来原样漏。这条和别的残留不同性质——
**它不需要输入畸形**：中文输入法正常打字就会出全角 `＠`，而「问法」那一行是用户原话、
要进 stdout（用户问「帮我查 alice＠x.com 这个号」就能触发）。真库 0 例，但输入空间不止库。

修法是把 at 号位置从字面 `@` 换成字符类 `_AT = [@\uff20\ufe6b]`（含全角 `＠` 和
﹫ U+FE6B SMALL COMMERCIAL AT）。**只替换本地部分、不动 at 号本身**，所以全角还是全角——
只挡 PII，不改写原文。修后实测：

```
'alice＠x.com'                 -> 'a***＠x.com'
'帮我查 alice＠x.com 这个号'     -> '帮我查 a***＠x.com 这个号'
'alice@x.com＠bob@y.com'       -> 'a***@x***＠b***@y.com'
'followers >= 100000 ＠ x＠y.com' -> 'followers >= 100000 ＠ x***＠y.com'   （阈值仍原样）
```

修完重跑了分隔符扫描（56 个，含 `＠`／`﹫`，0 漏）和真库 99,544 全量扫描
（本地部分泄漏 0、全角 at 泄漏 0、完全未改动 0、533 个非 ASCII 邮箱全打）。

**仍然不修的边界（判定为可接受）**

| 输入 | 结果 | 为什么可以不管 |
|---|---|---|
| `alice@@x.com`、`a@@@b.com` | 原样 | 连续 `@` 不构成合法地址；真库 99,544 个邮箱里 **0 例** |
| `alice\xa0@x.com`（本地部分和控制字符混） | 原样 | 同上，0 例 |
| `alice%40x.com`、`alice(at)x.com` | 原样 | 转义/遮挡写法，字面打码天然管不到，属另一个问题 |

这两类都要求"不是合法邮箱"或"不是字面邮箱"，不算漏洞。

判定口径也在这里钉死：**「本地部分 + `@` 原样出现」才算漏**（`local + '@' in out`）。
宽松一点的 `local[1:] in out` 会误报——单个字符的本地部分（`a@x.com` → `a***@x.com`）
本来就该留首字符。这条曾被误用，报出过一个假的「118 处泄漏」，复核后撤回。

### 3.2 暴露出来的问题（F1–F7；F1／F6／F7 已修，F2／F3／F4／F5 还挂着）

**F1 空回复（已修，2026-09-17）**

原来：`turn.py` 里第二次点查数工具（或保险丝用尽后再点搜索）会 `break` 掉整轮，
而 `reply` 初值是 `""`，**用户拿到空回复，没有任何提示**。两种情形都撞到过：
查库失败用尽后主 Agent 想再试一次；以及查库**成功**之后它又点了一次。

修法：拒绝第二次调用时，把该工具从**规划者能看见的工具集**里摘掉，然后继续这一轮，
让主 Agent 用手上已有的回填说话——而不是结束整轮。依据是 `CONTEXT.md`
「要查数时只调一次查数工具」：调用照样只算一次，但拒绝不再等于闭麦。
万一它到计划次数用完都没开口，兜一句 `NO_REPLY_FALLBACK`，
并用 `TurnResult.reply_is_fallback` 把「这是兜底、不是回答」标出来。

实测（同一句问法连跑三次，「邮箱不为空的账号有几个」）：

| 跑次 | 修前 | 修后 |
|---|---|---|
| 1 | FAIL：`名字核对` | FAIL：`名字核对` |
| 2 | FAIL：**`回复非空`** + `名字核对` | FAIL：`名字核对` |
| 3 | FAIL：**`回复非空`** + `名字核对` | FAIL：`名字核对` |

修后三次的回复都是「刚才查数时报错：库里没有 member 这张表，所以…暂时查不出来」——
主 Agent 从沉默变成如实说明。剩下那条 FAIL 是 F3（模型编了表名），不是 F1。

**但别把这三次读成"F3 必然发生"。** 复核时单独跑同一条问法，模型直接写对了
`xhs_creator`，`名字核对` 过了——F3 是模型随机性下反复出现的结局，不是必然结局。
这三次能钉住的只是 F1：修前有两次**回复为空**，修后一次都没有，而三条 FAIL 里
不再有 `回复非空`。F3 的频率要另起一组样本才能说，别混进来。

**判据必须跟着改，否则这个修复会把失败藏起来。** 空回复被兜住之后「回复非空」
永远过得去，所以补了一条硬判据「`主 Agent 说了话`」= `reply_is_fallback` 为假。
不加这条，修 F1 等于把一个可检测的失败换成不可检测的。

兜底那一支只有单元测试覆盖（`AlwaysCallQueryToolBrain` 那种死不开口的规划者）；
真模型三次跑都没走到它——实测真模型面对空工具集是会说话的，而且用得上手里的回填。
两个原有测试（`test_query_tool_call_count_is_observed_when_planner_calls_it`、
`test_second_query_tool_call_in_same_turn_is_rejected`）以前只断言调用次数、
不断言 `reply`，现在都补上了。

**F2 `SELECT *` 绕过 DDL 排除列**
`blogger_ddl.sql` 不列 `credit_level`／`keywords`／`summary_text` 等常量列和派生列，
只影响模型看不看得见，**挡不住模型写 `SELECT *`**。实测一次「先拿 5 条记录看看」，
回填里 17 列一列不少，包括全部被排除的列。要真挡住，得在执行器做列投影（L1 层改动）。

**F3 中文问句的 DDL / 文档两路材料全有全无（整份或全空），第三路是可部分命中的列表——不是「必然全空」**

> **2026-09-17 复核实测修正**：本节标题与首段原来写的是「必然三路全空」，**那是错的**——
> 拿单个 0/0/0 的观察当成了通例。正确形态见下。

`InMemoryVanna` 是关键词替身：它把中文问句切成 ≥2 字的整段（按「的是在与及了和」断），
再去和材料做子串匹配。中文问句切出来的片段基本不是词，所以对整份 DDL、整份文档这两路，
命中落不到「刚好那一段」上，**只会落到两端**。

**为什么会落到两端**：`train()` 在两条真实接法里都只被调用两次——
整份 DDL 一条、整份文档一条（`__main__.py:230-234` 与 `textsql_harness.py:172-181` 的 `build_stack`），
于是 `_ddl` / `_documentation` 各只有一个元素，`retrieve()`（`rag.py:104-110` 把它们 `"\n".join`）
对这两路**只能是「整份」或「空」**。第三路「问题-SQL」是**按条过滤的列表**（`rag.py:92-96`），
**它能出部分命中**，现在恒空只因为 `问法: []`；一填进 ≥2 条就会出现。

实测两组共 31 句中文问法（13 句 + 18 句，两组问法集不同，`问法` 均为空）：

```
第一组（13 句）   整份 7 句 · 全空 6 句 · 部分 0 句
第二组（18 句）   整份 8 句 · 全空 10 句 · 部分 0 句
```

**没有一句返回「部分」**。但**哪一端多随问法集变**（7/6 与 8/10 都出现过）——
别按「多数是全中」或「多数是全空」来设计，两种都是「不是检索」的症状，方向相反，**修的时候别只修一边**。

下面是三路全空那一端的形态，取自「穿搭类的博主，粉丝超过十万的有多少」：

```
材料      ddl 0 字  documentation 0 字  question_sql 0 字
SQL       SELECT COUNT(*) FROM sqlite_master WHERE type = 'table' LIMIT 1
名字核对  材料里没有：['sqlite_master', 'type']
回复      （空）        ← 修 F1 之前的观察；现在这一格不会空
```

模型手上没有表名，就去翻 `sqlite_master`。**这不是模型笨，是材料没到。**
`check_question.py` 的「材料三路」和「名字核对」两条把这件事变成了硬判据。

同一次跑里「类目对账」也证明问法本身没问题：`穿搭` 是 114 个类目名之一。
**坏在检索，不在问法。**

`InMemoryVanna` 只是替身（真 Vanna 未接）。但在真 Vanna 到位之前，
**任何中文问法的 E2E 判定都不算数**——三路全空时模型手上没表名，
整份全中时检索等于没做（同一份材料，问什么都一样），两种都不算「检索对了」。

**F4 答案类型没被约束**
问「给 3 条明细」，模型回 `SELECT COUNT(*)`，只答了数没给明细。
另一头，问「多少条记录」时模型会先 COUNT 再补一条明细查询（两次只读调用）。
金标里的 `答案类型`（实体集／标量／分组标量）现在没有对应的**判据**，
只能靠人看。要么做成判据（SQL 的列形状对得上答案类型），要么明确说这条是软的。

**F5 `.scratch` 里另外两个脚本的打码会漏（新发现，2026-09-17，未修）**

`validate_data.py:32` 和 `profile_table.py:36` 都用同一条**首尾锚定**的邮箱正则做单值打码：

```python
EMAIL = re.compile(r"^[^@\s]+@[^@\s]+\.[^@\s]+$")   # ^...$ + match()
```

单值的思路本身没错，但它的失败分支是 `return value`（原样返回）。于是**只要值不是
「干净的一个邮箱」，就整个原样打进 stdout**，而这两处打印的恰恰是「不干净的值」：

- `validate_data.py:320` 打在「不符合邮箱格式」的那些值上——不匹配正是被选中的理由
- `validate_data.py:330` 打在「含全角/排版符号或空格」的那些值上，判据里有 `" " in v`
- `profile_table.py:237` 的取样行

实测真实库：非空邮箱 99,544 个里，**131 个含内部空格或两个 `@`**，主要形态是
`name@domain. 尾巴`（如 `alice@x.com extra`）。这些值 `EMAIL.match` 全不过：

```
'alice@x.com extra'  -> 'alice@x.com extra'   （原样，本地部分泄漏）
'alice @x.com'       -> 'alice @x.com'        （原样）
'alice@x.com@y.com'  -> 'alice@x.com@y.com'   （原样）
```

两处都写着「样例（打码）」，实际漏了——**标了打码却没打，比不标更坏**。
（`mask_email` 对同样这 131 个值是 0 漏，因为它要的是「`@` 紧贴在本地部分后面」，
不要求整个值就是一个邮箱。）

**没修的理由**：这两个脚本在方案里被列为「只读参照，一字不动」，改它们超出本次范围。
一行修法（把失败分支从 `return value` 换成过一遍 `mask_email` 式的兜底）留给拍板。
**优先级低**：它不是 agent 的 stdout，是设计者手动跑诊断时的终端输出，且每次只出 5 条样例。

**F6 `名字核对` 把字符串字面量当成了"模型编的名字"（已修，2026-09-17）**

原来：`unknown_names` 对**整条 SQL** 跑 `_IDENT.findall`，字符串字面量也算进去。
实测「帮我查 alice＠example.com 这个账号，粉丝多少」，模型写的是**正确的** SQL：

```sql
SELECT followers FROM xhs_creator WHERE email = 'alice＠example.com' LIMIT 1
```

表名列名全对，但 `名字核对` 报出 `['alice', 'example', 'com']` —— 那是**筛选值**，
不是名字。一条对的 SQL 被判成 FAIL。

**这是判据自己造假失败**，和 F1「修复把失败藏起来」是同一类问题的镜像：
那次是让失败变得不可检测，这次是让成功变得会被检测成失败。两个方向都坏。

修法：`_structure_only()` 把字符串字面量和注释**合成一个交替、一次扫完**，然后才抽标识符。
双引号**不剥**——SQLite 里 `"foo"` 是标识符（找不到该列才回退成字符串），`"名字"` 要照抓。

**第一版修法是错的，记下来。** 我写成了「先剥注释、再剥单引号字面量」两趟，
理由是"字符串里出现 `--` 比注释里出现引号更少见"。这个判断反了，而且代价严重：

```sql
SELECT xhs_id FROM xhs_creator WHERE nickname = '--' AND member = 1
```

字面量里那个 `--` 被注释那趟吃成 `--[^\n]*`，**把整行后半段（含真编的 `member`）一起吞掉**，
`名字核对` 报「无」——真缺陷变成**假 PASS**。方向和 F1 一样危险（让失败不可检测），
只是这次是我自己引入的。

正确写法是一次交替、字面量那支排第一：`re.sub` 从左往右扫、在每个位置取第一个能匹配的分支，
字面量会被整段先消费掉，注释就没机会从它内部开始。

```python
_STRUCT = re.compile(r"'(?:[^']|'')*'|--[^\n]*|/\*.*?\*/", re.DOTALL)
def _structure_only(sql: str) -> str:
    return _STRUCT.sub(" ", sql)
```

**自检也修了，因为第一版自检同样是装饰性的。** 原来那条「注释不当名字」用的是
`nickname = '-- select from drop table' AND email = 'a@b.com' -- 注释`——剥过头之后
**后面没有需要抓的名字**，所以怎么剥过头都照样绿。复核时被指出后，换成了**载重判据**
「剥过头会暴露」：字面量里含 `--`、后面跟一个真编的 `member`，判据是
**「member 必须被抓到」而不是「结果为空」**。实测把 `_structure_only` 换回错的那版，
其余 8 条全绿、**只有这一条 ✗**——证明它载重，也证明旧自检抓不住这个洞。

自检现有 9 条，其中与 F6 相关的四条：

| 自检 | 防什么 | 方向 |
|---|---|---|
| 字面量不当名字 | 带筛选值的正确 SQL，必须报「无」 | 别造假失败（F6 本体） |
| 注释不当名字 | 字面量里塞关键字 + 行尾注释，剥完不许误报 | 别造假失败 |
| **剥过头会暴露** | 字面量里的 `--` 不许吞掉后文真编的名字 | **别让失败变得不可检测** |
| 真编名照样抓 | `FROM member` 必须照样抓出 `member` | **防止判据被修成永远通过** |

后两条方向相反、缺一不可：只补前两条，把 `unknown_names` 改成 `return []` 也能全绿；
只补「剥过头会暴露」而不管误报，又会退回 F6。

**仍然修不掉的：引号不配对。** 引号个数为奇数（未闭合、或值里含没转义的撇号）时，
字面量会**错误配对**，跨过真实结构一直吃到后面某个引号，把那之间的库名一起吞掉：

```
"...a = 'x ; SELECT * FROM member WHERE b = 'y'"   -> []   （member 被吞）
"...a = 'x\nFROM member WHERE b = 'y'"             -> []   （跨换行同样吞）
```

**这不是顺序问题**——两趟版和交替版在这些输入上**表现完全相同**（这里压根没有注释和字面量的先后可调），
所以换顺序修不了，**只有真词法分析器能修**。复核判定为「已记录的局限、不是这个判据的可操作缺陷」：
它要求 SQL 本身畸形，而畸形 SQL 会先在别的硬判据（可执行／期望分支）上暴露。
真实的 `nickname = 'O'Brien' AND member = 1` 这一支**不会**藏住 `member`（照抓，附带一个 `Brien` 误报）。

**这一条的经验值得单拎出来**：一个启发式判据的边界，要把「换个顺序能不能修」和
「根本修不了」分开测——两趟版和交替版在引号不配对上一致，才说明这不是我又一处顺序搞错，
而是启发式本身的天花板。

**F7 演示页接真管线后：坏路径静默断连（已修，2026-09-17）**

把 `__main__.py` 的演示页从「未接线版」接上真管线（`--db` / `--ddl` / `--docs`）之后，
复核子代理在真服务上打出来的：

```
$ uv run --python 3.12 python -m textsql_agent --db /tmp/does_not_exist_xyz.sqlite3 --port 8801
Text-SQL 问答已启动：http://127.0.0.1:8801
真组件已接线：真模型客户端 + 真只读执行器 + /tmp/does_not_exist_xyz.sqlite3。每轮把…摆出来。

$ curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8801/
200                          ← 页面照 200，还宣称"真组件已接线"
```

之后每一次查询都是**客户端收不到任何 HTTP 响应** + 服务端刷 traceback。根因扎了两层，
`__main__.py` 只是最外面那层：

1. `sqlite_executor.py:57` 的 `sqlite3.connect(...)` 在 `try` **块外**（try 从 58 行才开始），
   所以连接失败**不会**被转成 `SqlError` 而是直接抛；`sql_session.py:107` 的 `self._executor.execute(...)`
   也没兜。产品代码里本来就有这个洞，只是命令行跑不到「打不开的库」这条路径。
2. `__main__.py` 的 `do_POST` 整个没有 try/except，异常一路冒到 `http.server`。

**为什么必须修**：这是 **F1 的同一个形状**——一个失败被做成了不可检测——只是换到了 HTTP 边界上。
用户点「发送」后页面上什么都没发生，分不清是系统坏了、没查到，还是没人回答。
`NO_REPLY_FALLBACK` 那条注释讲的就是这件事，这里只是它在线上的又一次现身。

修法（都在 `__main__.py`，产品代码只动这一个文件）：

| 位置 | 改法 |
|---|---|
| `require_file()` + `main()` | `--db` / `--ddl` / `--docs` 起服务前先 `is_file()`，不过就打印「找不到文件」并 `SystemExit(2)` |
| `do_POST` | `json.loads` 包 try → 400 JSON；`handle_turn` 整体 try/except → 500 JSON |
| `send_json()`（新增） | 失败也回 JSON。**顺带修掉一个隐藏炸点**：`send_error(400, "缺少 utterance")` 的 reason phrase 是中文，而 `http.server` 默认 `HTTP/1.0`、用 latin-1 编响应行 → `UnicodeEncodeError`，连 400 都发不出去（`send_error(404)` 用的是 ASCII 默认文案所以侥幸没事） |
| 页面 JS | 认 `{"error": …}` 并显示出来；`response.json()` 本身也包了 try |
| `PAGE.replace("{{LEAD}}", …)` | lead 里带命令行原样传进来的路径，插 HTML 前 `html.escape` |
| `hops_of()` | 环 A 没查库时不报「命中基数 / 只读调用」——否则 `—` 既表示"没查"又表示"查了但失败用尽"，同一符号两种意思（复核指出的两义复用） |
| `render()`（`.scratch` 的夹具） | `当前问题` 改打**值**；缺这个键时整段打出来，不静默 |

**仍然没修的（记在这里，别当成已解决）**：

- **执行器连接失败仍然抛而不返回 `SqlError`**（根因第 1 条）。`do_POST` 的兜底让任何这种抛出
  变成一条能读的 500，**看得见**了，但「执行器该不该在连接失败时返回 `SqlError`」这个设计问题一字未动。
  它现在被 HTTP 层兜着，属于产品代码里的真实洞。

**F1 与 F3 同时命中的量化（2026-09-17 补测，修 F1 之前的那一版）**

同一句问法连跑三次：

```bash

```

| 跑次 | 硬判据不过的项 | 模型写的表 |
|---|---|---|
| 1 | `名字核对`（`['member']`） | `member` |

这一组数据钉住的是 F3：三次都编 `member`，说明它不是偶发，而是中文问句在替身 Vanna 下的
**反复出现的结局**（材料三路全空 → 模型没有表名可用 → 编一个）。说"反复出现"不说"必然"，

两次空回复里主 Agent 都是在查完之后又点了一次工具。**这两项会互相掩护**：
空回复的根因可能被误读成「模型笨」，其实是材料没到。F1 修掉之后，
同样三次跑全部如实回报「库里没有 member 这张表」，F3 再也没法藏在空回复后面了。
