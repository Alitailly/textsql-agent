## 11. `keywords`、`summary_text`、`extra_json` 的形态

### `keywords`（0 空值，去重 465,374）

构造公式：**`类目(空格连接) + " " + 昵称`**；无类目时就是昵称本身。

## 13. 对设计的直接影响

1. **类目枚举只有 114 个，可以整包注入 prompt。** 大约 1,600 个汉字，成本极低。**强烈建议把 114 个类目的封闭清单直接写进检索 Agent 的 system prompt**，让 LLM 只能从这个集合里选值（用 `IN (...)`），而不是自由发挥——因为库里没有别名表，LLM 一旦生成 "口红"/"彩妆" 这类词，SQL 就是全表扫 + 0 命中。

2. **`dict_category_alias` 是空表，术语归一化必须由 Agent 在 prompt 层解决。** 这是当前最大的功能缺口。实测：用户说"美妆"，若直接 `LIKE '%美妆%'` 只命中 8,659 行（仅 `美妆其他` + `美妆合集`），而正确的美妆类目集合（整体妆容/底妆/眼妆/唇妆/护肤*/面部保养/美甲/香水…）覆盖 **23,602 人**——**漏掉 63%**。同理"宠物"字面 0 命中，但 `猫` 7,411 + `狗` 6,143 是有的。**必须在 prompt 里内置一张"口语词 → 类目集合"的映射表**，或者新建这张字典表并落库。

3. **关联表可用，走 JOIN 而不是 `LIKE` 扫字符串。** 关联表 516,196 行、114 个类目、0 悬空外键、与 `raw_categories` 逐人完全一致——查询走 `xhs_creator_category JOIN xhs_creator` 是正确路径（有 `idx_cat` 索引）。`raw_categories LIKE '%x%'` 只在兜底时用。

4. **27% 的博主没有任何类目，类目过滤天生会漏人。** 126,676 人 `raw_categories IS NULL` 且关联表无记录。**类目筛选必须允许"未分类"作为显式兜底分支**（比如用户要"泛生活"类），否则这部分人永远检索不到，且这属于数据固有缺口、无法通过清洗补救。

5. **"能联系上"是硬约束，直接砍掉 79%。** 有邮箱的只有 99,544 人（21.16%）。**当用户说"能联系上的"，几乎必须带 `email IS NOT NULL`**，且检索 Agent 应该在回复里明确告知候选池从 47 万缩到 9.95 万。实践上这会和类目交叉过滤：美妆类 + 有邮箱 = 8,087 人，再加"粉丝<10万" = 6,980 人——**这个量级必须强制 `LIMIT`，且要告诉 LLM 每次返回 5~10 条是"从 7 千里的采样"而不是"全部"**。

6. **粉丝数是干净整数，SQL 可直接比较，但也意味着"粉不要太高"必须靠 LLM 翻译成数值区间。** 中位数只有 4,479，96% 的人在 10 万以下。所以"粉不要太高"这种话如果翻译成 `followers < 100000`，**几乎不产生过滤效果（命中 96%）**。prompt 里必须给出分位数锚点（p50=4,479 / p75=12,940 / p95=79,675），让 LLM 把"粉不要太高"落成 `followers BETWEEN 1000 AND 50000` 这种有区分度的区间，并明确要求带下限（库里有 279 人粉丝 <1000，属于僵尸号/残缺记录）。

7. **`followers_raw` 100% 是纯数字，绝对不要写单位换算逻辑。** 上游已完成换算，所谓"原文层"并不保留小红书展示文本（唯一残留原始痕迹是 `province` 的"省 市"粘连串，而 `creator.province` 已清洗干净）。入库管线里的 `w`/`万` 解析是死代码，应当删掉。

8. **`is_public`、`credit_level`、`extra_json`、`data_date`、`batch_id` 全部是常量或全 NULL，不要给它们设计任何筛选/排序/展示逻辑。** `is_public` 恒为 1、`credit_level` 470,398/470,399 都是 2、`extra_json` 全 NULL。把它们放进 prompt 只会浪费 token 并诱导 LLM 生成无意义的过滤条件。**注意 `idx_public_fans(is_public, followers)` 这个复合索引因 `is_public` 恒定而实际退化成 `followers` 单列索引。**

9. **规模 47 万行，是"中等"量级：不需要分布式，但必须强制 LIMIT 和分页。** 单机 SQLite 上带索引的类目 JOIN + 粉丝区间查询是毫秒级，可以直接给 Agent 配只读 SQL 执行器。但**必须在工具层硬编码 `LIMIT`（建议默认 200，返回给 LLM 前再截断到 10）**，因为 LLM 极易生成不带 LIMIT 的 `SELECT *`，47 万行回灌会直接撑爆上下文。同时建议对 `nickname`/`summary_text` 做结果截断。

10. **`xhs_id` 是唯一的稳定业务主键，但它是 4~19 位、75% 纯数字 25% 字母数字混合的字符串。** 54 条为 NULL，114 个类目的台账里没有任何手机号字段。**外部搜索补充动态时，只能用 `nickname` 或 `xhs_id` 作为检索键**，而 `nickname` 有 11,623 个重复（`momo` 一个昵称 263 人）、7.8% 含 emoji——**用昵称做外部搜索会因为重名严重而串号，应当优先用 `xhs_id` 拼小红书用户主页 URL**，并在结果合成时向用户说明身份匹配的不确定性。
