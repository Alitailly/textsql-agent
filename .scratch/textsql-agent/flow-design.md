# 流程设计：查库 + 富化 + 合成

词以 `CONTEXT.md` 为准。总流程以 `textsql-agent-flow.md` 为准，本文只描述**对它的扩展**。摘要形状以 `docs/adr/0002-free-text-summary-and-clean-src.md` 为准。

Status: 骨架已定；表结构已到（见 `data-profile.md`），`【待库】` 已按真实数据填完，仅剩两项需要产品决策（见第九节）。

**实测数据锚点**（470,399 位博主，快照日 2026-09-14）：类目 114 个封闭枚举；有邮箱 99,544（21.16%）；粉丝 p50=4,479 / p75=12,940 / p95=79,675；26.92% 的博主无类目。这些数字是本文所有阈值参数的依据。

---

## 一、这个场景要解决什么

库里存的是**私有但可结构化的事实**（例：博主名、平台 id、粉丝数、内容类目、联系邮箱）。这类信息搜索引擎给不了、通用大模型只能瞎编——这正是系统的价值锚点。

但库本身**不足以独立回答用户的问题**：它知道"有谁"，不知道"这个人最近怎么样"。所以要拿库锁定的确切身份，去公开渠道补充动态信息，再由主 Agent 合成。

一句话概括：**库提供不可幻觉的锚点，搜索提供时效性，主 Agent 提供合成。**

---

## 二、现有流程到这里为止

`textsql-agent-flow.md` 已定义的环 B：

```text
B1 用户说话
 → B2 主 Agent 写当前问题，调查数工具一次
 → B3 小模型改写（改写问题 + 查询摘要）
 → B4 Vanna 三路检索一次
 → B5 查库对话（只调只读查库工具）
 → B6 回填主 Agent
```

**缺口**：B5 出来的是列式行集（`RowSet`），B6 直接把行截断成文本回填。这条路径假设"用户要的是一个人看的数字"。本场景要的是**一组实体**，每个实体还要带外部补充。中间少了三步：解析成实体、逐实体富化、按来源组装。

---

## 三、目标流程

不新增顶级编号。富化是 B6 内部的展开——理由与 B5 把多次只读调用收成一个小环相同：这些步骤由程序编排，主 Agent 看不见也插不进手。

```text
B3 小模型改写
     → 改写问题 + 查询摘要
B4 Vanna 三路检索一次
B5 查库对话（只读查库工具，5 次 / 30 秒保险丝）
     │
     ▼
B6 回填（扩展）
     ├─ B6.1 判结果
     │     ├─ 有行 ────────→ B6.2 解析实体 → B6.3 富化 → B6.4 组装
     │     ├─ 0 行 ────────→ B6.5 写未命中记录 → 回填「没查到」
     │     └─ 失败用尽 ────→ 回填「最后 SQL + 报错」，两槽不动
     └─ 成对覆盖槽位（仅查库成功时）→ 交给主 Agent
```

**顺序不变**：`spec.md` 说的「编排 B3→B6」仍然成立，只是 B6 内部变厚了。

## 四、B6 各步做什么

### B6.1 判结果

沿用现有三分支（`sql_session.py` 已经区分得很清楚，不用改）：

| B5 返回 | 进哪一支 | 槽位 |
|---|---|---|
| 有行 | B6.2 | 成对覆盖（新 SQL + 本轮摘要） |
| 0 行 | B6.5 | 成对覆盖（空查询 SQL + 本轮摘要） |
| 失败用尽 | 直接回填 | 旧值不动，本轮摘要扔掉 |

### B6.2 解析实体

把 `RowSet`（列名 + 行）转成实体列表：每一行变成一个「字段名 → 值」的映射。

```text
RowSet(columns=("name","fans","category","email"), rows=(("小鹿",128000,"美妆","a@x.com"), …))
    ↓ B6.2
(
  {"name": "小鹿", "fans": "128000", "category": "美妆", "email": "a@x.com"},
  …
)
```

这一步必须是程序做的，不能让模型从文本里重新抠——抠错了就会把 A 的信息安到 B 头上。

**实体保留哪几个字段**（表结构已定，`xhs_creator` 18 列 + 关联表 1 列，取舍如下）：

| 字段 | 进实体？ | 理由 |
|---|---|---|
| `xhs_id` | **必进，作身份主键** | 470,345 个非空值 0 重复。是唯一稳定标识。**它就是平台对外的「小红书号」**，不是内部 id |
| `id` | **不进，且禁止当主键** | 实测与粉丝的斯皮尔曼相关 = **-1.0**：这张表是按粉丝**降序**排的，`id` 只是排序序号。换一次排序就全变，拿它做关联或缓存键必错 |
| `nickname` | 进，仅供显示 | 22,996 条重名（`momo` 一个昵称 263 人），**不可作身份键** |
| `followers` | 进 | 干净整数，直接可比 |
| 类目（走关联表 `category_name`） | 进 | 一个博主 1–9 个类目，须 `DISTINCT` 去重后拼成列表 |
| `province` / `city` | 进 | 省≈34 个干净值、市 383 个，可作过滤也可作搜索词 |
| `email` | 进（回填可见） | **它就是产品**——用户要的就是能联系上的人。但见下方约束 |
| `raw_categories` | **不进** | 冗余，与关联表逐人一致；只用关联表 |
| `credit_level` | **不进** | 470,398/470,399 恒为 2，常量 |
| `is_public` | **不进** | 恒为 1，常量 |
| `data_date` / `batch_id` / `imported_at` | **不进** | 全库单值（同一次快照），无时间维度 |
| `extra_json` | **不进** | 100% NULL，死列 |
| `keywords` | **不进，无独立信息** | 已实测：**全部 470,399 行都严格等于** `类目(逗号换空格) + 空格 + 昵称`，零例外。它只是同一批字段的重新拼装，不是独立信号 |
| `summary_text` | **不进，无独立信息** | 已实测：全部 470,399 行都套同一个模板，由昵称/粉丝/类目/地区拼成。类目子句直接来自同一个类目字段（含"内容类目"的 343,723 行 = 有类目的人数） |

**邮箱的三条约束**（不是脱敏问题，是流向问题）：
1. 进**回填材料**：明文。用户拿它去联系，脱敏等于废掉功能。
2. 进**外部搜索词**：绝不。把邮箱拼进搜索 query 等于把用户私库泄进公开渠道。
3. 进**未命中日志 / 画像**：脱敏（`a***@qq.com`）。日志是给运营看分布的，不需要明文。

**邮箱需要一步归一化，不能直接拿去发信。** 99,544 个非空邮箱里，**977 个（0.98%）不符合邮箱格式**，其中 **581 个含全角/排版符号或空格**——形如 `163•com`（全角圆点替掉了 `.`）、`163. com`（多了空格）、`qq·CoM`（中点 + 大小写混杂）。这些值能通过 `LIKE '%@%'` 这种粗筛，但**发信必退**。

所以 B6.2 解析实体时要加一步：**全角转半角 + 去空格**，转完再校验；仍不合格的标为"有邮箱但格式可疑"，不要静默当作有效联系方式。这一步放在程序侧，不能指望模型顺手做对。

**注意这是第三方数据的特征。** 这类排版污染通常来自 OCR 或二次转录，反过来说明这批 `email` 不是平台接口直接给的原文，而是经过人工/半自动转录的——这也是"邮箱可能不准确"的一个独立旁证。

### B6.3 富化

对每个实体去公开渠道搜索补充信息。

```text
每个实体
  → 用 xhs_id（小红书号）+ nickname 拼搜索词
  → SearchEngine.search(query, timeout=…)
  → 成功：留标题 + 网址 + 截断摘要
  → 失败/无结果：标「未找到公开信息」，不是错误
```

**搜索词怎么拼**（已定，但有一处必须先验证，见下）：主键用 `xhs_id`，**不要用 `nickname` 单独作搜索键**。理由是实测的重名规模：22,996 条重名记录、11,623 个重复昵称、`momo` 一个名字 263 人、7.8% 的昵称含 emoji（且 emoji 前常带全角顿号或空格，直接拼词会污染 query）。用昵称搜会串号——把 A 的动态安到 B 头上。这正是 B6.2 那句"不能让模型从文本里重新抠"要防的同一类错误，只是换到了外部搜索这一侧。

**⚠️ `xhs_id` 是「小红书号」，拼不出主页 URL。** 这一点已用两个已知博主交叉验证：

```text
采集器记录的博主            dump 里的 xhs_id
尖下巴的反击  red_id=262***94   →  xhs_id=262***94   ✓
林小云mumu    red_id=mum***oo   →  xhs_id=mum***oo   ✓
```

即 dump 的 `xhs_id` 就是平台对外的「小红书号」，长度 4–19 位（9 位最多，占 52%）。

但小红书主页 URL 的形式是 `https://www.xiaohongshu.com/user/profile/<24位hex内部id>`（如 `5657c8a50bf90c5b8b050798`）——**那是内部 user_id，不是小红书号，而 dump 里没有任何一列装着它**。所以：

- **不能**用 `<xhs_id>` 拼主页 URL，拼出来是坏链接。
- 可靠的路径是**用小红书号去搜**（平台站内搜索 `search_result?keyword=<小红书号>&type=51` 能解析到主页），但那不是通用 `SearchEngine` 的能力。
- **【待验证】通用搜索引擎（本项目的 `SearchEngine`）搜小红书号能否命中主页**——这决定 B6.3 是"能直接拿到主页 URL"还是"只能拿到间接结果"。验证方式：拿几个 `xhs_id` 去配好的搜索引擎试，看返回里有没有该博主的主页。

**B6.4 的措辞要以验证结果为准**：如果通用搜索只能给间接结果，那材料里就不能声称"这是该博主主页的动态"，只能说"按小红书号检索到的公开信息，身份未经平台确证"。这个区别不是措辞洁癖——它正是「库提供不可幻觉的锚点」这个卖点能不能守住的地方：**库内事实是确证的，外部补充是检索到的**，两者混说就把卖点毁了。

`nickname` 只作**辅助限定词**：搜索词形如 `<xhs_id> <nickname>` 或 `<xhs_id> 小红书`，让搜索引擎在重名时更可能命中对的那个。`xhs_id` 为 NULL 的 54 人，退化为只用 `nickname`，并在材料里标「身份未确证」。

**必须向用户说明身份匹配的不确定性**：外部补充是"按主页地址搜到的内容"，不等于"平台官方确认的该账号动态"。B6.4 的措辞要把这层不确定性写出来，不能假装是权威事实。

**硬约束（L1，改要写 ADR）**：

- 富化发生在 **B5 结束、查库对话已被丢弃之后**，由程序编排。查库大模型全程只有只读查库工具。
  → 这不违反 `CONTEXT.md`「查库大模型」词条的 `_Avoid_: 给它其它工具或联网搜索`：搜索不是它的工具，它那时已经退场了。
- 富化结果**不进槽位**。槽位只放上次 SQL + 摘要（给下一轮小模型）。富化结果只进本轮回填（给主 Agent 说话）。
  → 维持「两路分开」：给人说话的材料 ≠ 给下一轮小模型的材料。
- 富化失败**不影响槽位覆盖**。槽位只看查库是否成功，与外部搜索无关。

**可调参数（L3，只动配置和测试）**：

| 参数 | 现取值 | 说明 |
|---|---|---|
| 查库硬 `LIMIT` | 200（回填前再截断到 10） | **不是可选项**。见下方"为什么必须硬编码 LIMIT" |
| 每轮最多富化几个实体 | 5 | 否则用户要 20 个就等于 20 次外部调用 |
| 每个实体留几条命中 | 3 | 单条摘要沿用 `WEB_SEARCH_SNIPPET_CHARS` |
| 单次搜索超时 | 15 秒 | 与环 A 搜索一致 |
| 超出上限的实体 | 只回填库内事实并注明"未做外部补充" | 不静默丢弃 |

**为什么必须硬编码 LIMIT**：实测一个很普通的问法——"美妆、能联系上、粉丝 10 万以内"——命中 6,998 人。而查库大模型极易生成不带 `LIMIT` 的 `SELECT *`，47 万行回灌会直接撑爆上下文。所以 LIMIT 放在**工具层强制**，不能指望模型自觉。同时要在回填材料里说清"这是从约 7 千人里的 5 条采样"，**不能让用户以为看到的就是全部**——否则用户会误判"美妆博主只有 5 个"。这是采样说明，不是免责声明。

**"粉不要太高"必须靠分位数锚点翻译**：库里中位数只有 4,479，96% 的人在 10 万以下。所以把"粉不要太高"直译成 `followers < 100000` 几乎不过滤（命中 96%），等于没筛。prompt 里要给出 p50=4,479 / p75=12,940 / p95=79,675，让模型落成 `followers BETWEEN 1000 AND 50000` 这种有区分度的**区间**，并**强制带下限**——库里有 279 人粉丝不足 1,000，属僵尸号或残缺记录。

**与环 A 搜索的关系**：两处用同一个 `SearchEngine` Protocol（`web_search.py:36`），但**必须各自计数**。环 A 的 `WebSearch` 类带自己的 `_calls` 和 3 次上限（`WEB_SEARCH_MAX_CALLS_PER_RING_A`），富化要另起一个计数器，绝不能共用一个实例——否则环 A 搜索几次就会把富化额度吃光。

### B6.4 组装回填材料

产出给主 Agent 的材料，**按来源分段**：

```text
库内命中 3 条（来自只读查库）：
1. name=小鹿 | fans=128000 | category=美妆 | email=***
   公开补充：<标题> <网址> <摘要>
2. name=阿远 | fans=96000 | category=美妆 | email=***
   公开补充：未找到公开信息
3. …

说明：第 1 条的身份信息来自本库，公开补充来自网络搜索，两者来源不同。
```

这一段的形状就是产品本身——**来源标注不是免责声明，是卖点**。用户要能一眼看出"哪些是别人给不了的、哪些是网上也能查到的"。所以：

- 库里来的字段和搜来的补充，在材料里必须物理分段，不能混成一句话。
- 主 Agent 的提示词要明确要求它保留这个区分（`prompts.py` 现在只有"库里的精确数只来自查数工具回填"，要补一条针对外部补充的）。

### B6.5 未命中记录

查库成功但 0 行时，记录这次"想找但没找到"的问法。

```text
触发：B5 返回 0 行（查库成功、没命中）
记录：时间、用户原话、当前问题、改写问题、SQL
用途：运营据此知道「用户想找什么样的实体而库里没有」→ 订补数据
```

**架构边界（必须守住）**：

- 这是**程序侧审计日志**，不是业务写库。
- 业务库仍然只读账号、禁写语句、表白名单一套不变。日志走**独立的写入路径**（倾向独立文件而非业务库里的表，理由见第九节第 7 项）。
- 查库大模型和任何模型都碰不到它——它不挂在任何模型的工具列表里。
- 这个边界不写清，会让下一个接手的人以为"禁写"被破坏了。

0 行时仍然**如实回填「没查到」**（现有规格不变），不做自动降级搜索、不自动放宽条件。用户要的是"知道哪里有问题"，不是"系统自作主张"。

### B6.6 一个数据固有缺口：26.92% 的博主没有类目

126,676 人（26.92%）在关联表里没有任何记录。这是**数据固有缺口，清洗补不回来**。所以：

- 任何带类目条件的查询**天生漏掉这四分之一的人**。这不是 bug，是事实。
- 当用户问的是"泛生活"这类**跨类目**意图时，"未分类"必须作为**显式兜底分支**出现在 SQL 里（例如 `OR 无类目`），否则这部分人永远检索不到。
- 反过来，当用户问的是**明确的单类目**时，"未分类"不该被兜进来——那会稀释精度。
- 两者怎么区分，是检索 prompt 要判断的事，不是工具层能决定的。**这条要写进 B4/B5 的 prompt 提示**。

## 五、B4 检索材料从哪来（表结构已定）

原来 `__main__.py` 演示的是 `CREATE TABLE sales`，与本库无关。真实库下 Vanna 三路材料的具体来源：

| 路 | 材料 | 现成度 |
|---|---|---|
| **DDL 路** | `xhs_creator` 18 列 + `xhs_creator_category` 2 列的真实 DDL | 直接导出 |
| **文档路** | **要自己写**。原先以为 `summary_text` 是现成语料，**实测证伪**（见下） | 没有现成的，要手工写库说明 |
| **问题-SQL 样例** | **没有**，要等第九节第 8 项的真实问法 | 待用户 |

**`summary_text` 和 `keywords` 都不能当文档路材料——它们是派生列，不是独立信息。** 这是我先前的一个误判，实测推翻了：

```text
keywords     == 类目(逗号换空格) + 空格 + 昵称      470,399 / 470,399 行全部吻合，零例外
summary_text 套「X：小红书博主，粉丝N，[内容类目：…]，地区：Y」模板   470,399 / 470,399
含「内容类目」的行 343,723  ==  实际有类目的人数 343,723
```

第三条是决定性的：`summary_text` 里那句"内容类目：…"**直接来自类目字段**，不是独立观察。对没有类目的 126,676 人，这句直接不出现，`keywords` 也退化成"只有昵称"。所以这两列对 Vanna 不提供任何新知识，喂进去只是把同样的信息换个说法说两遍。

**附带纠正**：`眼妆`/`底妆` **是**类目（1,701 / 1,639 人），不是"更细的关键词"。我先前把它们说成关键词是错的——114 个类目里本来就有它们。

**还要提醒**：**不要给 Vanna 喂** `credit_level`（99.9998% 恒为 2）、`is_public`（恒为 1）、`extra_json`（全 NULL）、`data_date` / `batch_id`（全库单值）。喂进去只会诱导模型生成 `WHERE is_public = 1` 这类无意义过滤条件，浪费 token 还降低准确率。演示页那个 `CREATE TABLE sales` 换成真 DDL 时**要顺手把这些列排除**——这正是 ADR 0002 第 7 条「演示 train 按本场景的库渲染」的具体做法。

## 六、必须新开的边界

现有的边界是 `QueryLlm`、`ReadonlyExecutor`、`SearchEngine`、`SmallModel`、`VannaRag`。本流程要加两个：

| 新边界 | 职责 | 为什么不能省 |
|---|---|---|
| `EntityParser` | `RowSet` → 实体列表 | 解析错误会把 A 的信息安到 B 头上，必须是可替换、可测试的一层 |
| `MissLog` | 写未命中记录 | 它是唯一一处**写入**，必须和只读通路显式分开 |

富化本身不需要新边界——直接用 `SearchEngine`，只是换个调用方和计数器。

**`EntityParser` 的字段映射**：见第四节 B6.2 的字段取舍表。它要做的转换是——`RowSet` 一行 → 一个实体 dict，其中类目由 `xhs_id` 回查关联表补齐（`DISTINCT` 去重），`xhs_id` 落为实体的 `id` 字段。

**`MissLog` 的落地位置和格式**：格式已定，位置待用户定（见第九节第 7 项）。格式如下，**只记"想找而库中没有的问法"，不记任何博主 PII**：

```text
时间 | 用户原话 | 当前问题 | 改写问题 | SQL
```

理由：这张表的用途是让运营看出"用户在找什么而库里没有"，从而**决定补什么数据**。所以字段要能反推"缺哪一类博主"，不需要记邮箱——记了反而让这个审计通路平白变成一处 PII 聚集点。

### 关于「不都是有邮箱的吗」：不是，只有 21%

这一条单独记下来，因为它和「这份库是哪来的」直接相关。

```text
有邮箱   99,544   21.16%
无邮箱  370,855   78.84%
```

已排除"看错列"的可能：`xhs_staging.email` 与 `xhs_creator.email` 填充数完全一致（都是 99,544）；`nickname`/`keywords`/`summary_text`/`raw_categories` 里也没有藏邮箱（含 `@` 的行只有 31 行，是昵称里的 @ 提及，不是联系方式）；dump 里一共只有 4 张表，**都已导入**，没有漏掉的表。

而邮箱率**随粉丝单调上升**，是个真信号而不是随机缺失：

| 粉丝档 | 人数 | 有邮箱 | 邮箱率 |
|---|---|---|---|
| <1千 | 279 | 35 | 12.5% |
| 1千–1万 | 325,404 | 56,653 | 17.4% |
| 1万–5万 | 107,489 | 28,790 | 26.8% |
| 5万–10万 | 18,487 | 6,436 | 34.8% |
| 10万–50万 | 16,312 | 6,625 | 40.6% |
| >50万 | 2,428 | 1,005 | 41.4% |

**"都有邮箱"这个印象，来源应该是你自己那套采集流程**——它按「简介含邮箱 且 粉丝>1000」过滤，产出必然是接近 100% 有邮箱（那套流程自己的产出文件里那 2 行就是 100%）。**但这份 470,399 行的 dump 不是那套流程的产出**，它是按粉丝降序的一次全量扫描，头部第一行就是粉丝 1,173 万的阮小美，而他**没有邮箱**。

支撑"来自另一处"的旁证是 `id` 与粉丝的斯皮尔曼恰为 **-1.0** —— 全表严格按粉丝降序排列。这是导出/导入的排序痕迹，你那套逐号采集不会产生这种严格单调的排列。

**交叉验证时还发现两处对不上**（同一个博主，采集器 2026-09-01 那次 vs dump 的 2026-09-14 快照）：

| 博主 | 粉丝（采集器 → dump） | 地区（采集器 → dump） |
|---|---|---|
| 尖下巴的反击 | 128,709 → **89,681** | 江苏 → 江苏 ✓ |
| 林小云mumu | 491,397 → **253,873** | 广东 → **上海** |

粉丝是**降**的，地区还变了。粉丝数在两周内腰斩更像是两边口径不同（比如一方是实时抓取、另一方是第三方平台的估算值），而不是真实掉粉。**这直接影响 `email` 的语义**：如果这份 dump 来自第三方平台，那它的 `email` 可能是平台另填的商务联系方式，而不是博主写在简介里的邮箱——那个可能过期或非本人。

**所以有一件事要请你确认**：这份 dump 是从哪来的（自己的库导出 / 第三方平台 / 购买的名单）？这决定 B6.4 要不要对邮箱和粉丝数标注"来源为第三方、未经平台确证"。

### 最大的一个缺口：类目同义词映射

`dict_category_alias` 是**空表**，而它不是可选项——它是这个库里最容易出错的地方。实测一个最普通的问法：

```text
用户说"美妆"
  直接 LIKE '%美妆%'  →  8,659 人（只命中「美妆其他」+「美妆合集」）
  正确的美妆类目集合   →  23,602 人
  →  漏掉 63%
```

因为库里的类目是**细粒度子类**，根本没有一个类目叫"美妆"。正确集合要横跨十三个子类：`美妆其他`、`整体妆容`、`面部保养`、`护肤合集`、`美甲`、`护肤其他`、`眼妆`、`底妆`、`唇妆`、`美妆合集`、`香水`、`面部清洁`、`口腔护理`。

更极端的是"宠物"——字面命中 **0**，而 `猫` 7,411 + `狗` 6,143 = 13,554 人是有的。

**所以这张映射表要么建表落库（L2 配置），要么至少内置进检索 prompt。** 两者都要在库里没有对应词时给出明确行为，不能让模型自由发挥生成 `LIKE '%彩妆%'` —— 那是全表扫 + 0 命中。这是 L2 层的活：改数据不改代码。

### 第 7 项：未命中记录放哪

格式已定（第四节 B6.5）。位置有两个选择，需要你定：

| 方案 | 好处 | 代价 |
|---|---|---|
| 独立 SQLite 文件 | 与业务库物理隔离，绝不可能误写业务库 | 多一处要备份的东西 |
| 业务库里的独立表 | 查询方便，一处备份 | **业务库必须因此多一个写账号**，违反"只读账号"的干净边界 |

我倾向**独立文件**：业务库的只读边界是这个设计里最值得守的东西之一，为了一个审计日志破开它不划算。

### 第 8 项：验收问法还要你来给

**这一项我不能替你编。** 原来那个销售示踪弹就是这么出问题的——它是为了让一轮行为可观察而编的，编着编着被当成了真实库结构。

需要你给 **3–10 个真实问法**，会是验收用例。从数据看，值得覆盖的形态有这几类（供你参考，不是替你写）：

- 单类目 + 联系条件（"能联系上的美妆博主"）
- 跨类目口语词（"宠物博主" —— 库里没有"宠物"这个词）
- 粉丝量级的模糊说法（"粉不要太高" —— 需落成有区分度的区间）
- 地理过滤（"上海的穿搭博主" —— 广东 76,482 人最多）
- 命中很少或 0 行的问法（造出真实的未命中记录）
- 一句话叠多个条件（触发采样说明）

填完这两项，本文 Status 才能从"骨架已定"转正。

## 十、数据缺陷清单（第三方数据的已知问题）

这批库是**第三方筛选过的数据**，所以下列缺陷是数据源固有属性，不是我们这边的 bug。逐条记下来，因为它决定流程里哪些地方必须兜底。核对脚本：`tools/validate_data.py`（只读，可重跑）。

### 结论：可以用，但有三处必须在程序侧兜底

库本身是**干净的、可用的**：470,399 行无重复主键（`xhs_id` 零重复）、关联表 516,196 行**零悬空外键**、`staging → creator` 的行数与 `email`/`nickname` 逐行一致（没有丢行）、`followers` 无负数、`gender` 只有 3 个正常取值。作为「找博主」的实体库，结构是成立的。

**七条缺陷里三条是「高」，都必须由程序兜底，不能交给模型自觉**：

1. **D3 邮箱归一化** —— 581 个邮箱带全角符号，粗筛能过、发信必退。归一化必须是程序侧的一步。
2. **D6 无类目四分之一** —— 126,676 人（含头部 140 人）没有类目，且**库内没有补救路径**（D5 已证明 `keywords`/`summary_text` 不提供独立信息）。跨类目意图必须让"未分类"作显式兜底分支。
3. **D7 昵称不可作键** —— 11,623 种重名、`momo` 一个人名 263 次。身份键只能是 `xhs_id`，外部搜索也不能单用昵称。

其余四条（D1 港澳台截断、D2 海外归属地、D4 常量列、D5 派生列）是「中」，处理方式分别是：一次性 ETL 修复、prompt 提示、不喂模型。

### D1 港澳台的地区名被截断（2,498 行，0.53%）

原始串是三级（`中国 台湾 台北`、`中国 香港`），拆分时取了首尾两段，中间的丢掉：

```text
staging 原始串      →  creator.province   creator.city
中国 台湾 台北      →  中国                台北        ← "台湾" 丢了
中国 香港           →  中国                香港        ← "香港" 降级成市名
```

所以库里有 **2,498 行 `province = '中国'`**：香港 1,869、澳门 262、台湾各市约 350。

**影响**：按省过滤时这批人的地区等于一个无意义的"中国"；按"香港博主"查会 0 命中（`province LIKE '%香港%'` 确实返回空）。

**可修**：原始串在 `xhs_staging.province` 里是完整的，重做一遍拆分即可复原。属于一次性 ETL 修复。

### D2 `province` 含海外归属地（15,967 人）

`province` 不是纯中国省份，还混着海外 IP 归属地：美国 4,392、澳大利亚 2,462、日本 2,012、加拿大 1,938、英国 1,602、韩国 892……共 147 个去重值（中国省级只有 34 个）。

**影响**：地理过滤不能假定值域是中国省份；用户说"国内的"时需要显式排除海外。

### D3 邮箱需要归一化（977 个格式不合，其中 581 个含全角符号）

见第四节 B6.2 的邮箱约束。第三方转录留下的排版污染（`163•com`、`163. com`、`qq·CoM`），粗筛能过、发信必退。

### D4 四列是常量、一列全空

`credit_level`（99.9998% 恒为 2）、`is_public`（恒为 1）、`data_date`（单值 2026-09-14）、`batch_id`（单值 1）、`extra_json`（全 NULL）。喂给模型只会制造无意义过滤条件。

**注意 `data_date` 单值意味着这张表没有时间维度**——旧四项摘要里的「时间」在这里无处可绑。

### D5 两列是派生列，无独立信息

`keywords` 严格等于 `类目 + 昵称`；`summary_text` 是全部字段的模板化重排。对没有类目的 126,676 人，两者都退化成"只有昵称"。

**影响**：不能当检索信号，也不能当 Vanna 文档路材料。

### D6 无类目 126,676 人（26.93%），且无库内补救路径

含头部 1,000 人里的 140 人（14%）。无类目率随粉丝下降（1千–1万 27.3% → >50万 13.5%），是第三方平台**覆盖偏好**的痕迹。

**不可补救**：这些行的 `keywords` / `summary_text` 都退化成只有昵称（D5），库内没有任何字段能反推类目。只能靠 prompt 兜底（见第四节 B6.6）或日后补数据。

### D7 昵称重复 11,623 种，emoji 占 7.8%

`momo` 一个昵称 263 人。所以昵称不能作身份键，外部搜索也不能单用昵称（见 B6.3）。

| # | 缺陷 | 严重度 | 在哪处理 |
|---|---|---|---|
| D1 | 港澳台地区被截断 | 中 | 一次性 ETL 修复（数据可重建） |
| D2 | province 含海外 | 中 | 检索 prompt 提示 |
| D3 | 邮箱需归一化 | **高** | B6.2 程序侧归一化步骤 |
| D4 | 常量列 / 死列 | 中 | 不喂 Vanna、不进实体（B6.2 表已列） |
