# 查询摘要回到自由文本；业务词一律不进 src/

Status: accepted（2026-09-17 落地，见文末「落地记录」）
Date: 2026-09-17
Supersedes: 本 ADR 取代此前同号的「名目随 schema」草案（该草案把摘要结构化的必要性高估了，见决策二）

---

## 背景

两件事一起逼出了这个决策。

**第一件：四项摘要长自销售场景，不是长自数据库。** `CONTEXT.md` 把查询摘要锁成「指标、时间、过滤、口径」。`undesigned.md` 承认了「口径举例含税/未税」和 `ContractSmallModel` 是专有的，却把「四项 + 恰好五行」的形状当成通用的。这个判断不成立：「指标」的语义是"要算的聚合量"，「口径」在销售场景里指税务口径——两个名目本身就带着聚合分析业务的假设。换到博主库立刻塌掉：博主场景要的是"找一批实体"，没有聚合量可算，也没有含税概念。

**第二件（更根本）：程序从来不消费摘要的结构。** 全仓查过，摘要在程序里只被**原样传递**，没有任何一处基于它的内容做分支判断：

| 位置 | 对摘要做了什么 |
|---|---|
| `rewrite.py:65-81` `build_rewrite_prompt` | 把四个字段拆开、再 f-string 拼回 prompt。**唯一的使用点** |
| `rewrite.py:84-104` `parse_rewrite_output` | 把模型输出解析成 `QuerySummary` |
| `query_tool.py:98` | `query_summary=rewritten.summary` 原样落进 outcome |
| `turn.py:165` | `query_summary=current_slots.query_summary` 原样透传 |
| `__main__.py:132-135` | 原样存进 `ProgramSlots` |

也就是说，程序给摘要加了结构，却没用这个结构。结构只活在几行 f-string 和测试断言里。

而在筛选维度多的场景，固定四项还会**挤爆**：

```text
四项结构（博主场景）
  指标：博主            ← 名目本身就怪，博主不是"算出来的量"
  时间：未说明
  过滤：类目=美妆；粉丝<20万；邮箱非空；按城市分组   ← 全挤在一格，语义还丢
  口径：未说明

自由文本
  改写问题：查询美妆类目、粉丝20万以内、有联系邮箱的博主，按城市分组
  需求说明：用户要找能直接联系的美妆博主，中腰部（粉丝不超过20万），想按城市看分布
```

维度一多，四项装不下，全塞进「过滤」。**自由文本在这里不是省事，是质量更好。**

---

## 决策

**一、摘要分两段骨架，只有第一段必须可提取。**

```text
改写问题：<一句完整中文问句>        ← 程序要用：拿它当 Vanna 的 query
需求说明：<自然语言，说清用户要什么 + 上一轮已限定了什么>   ← 只给下一轮小模型看
```

分界线是：**程序要用的部分结构化，只给模型看的部分自由。** 「改写问题」必须能被可靠提取，因为 `query_tool.py:94` 要拿它去 `vanna.retrieve()`；提取不到，整条管线就断了。摘要那段只喂回下一轮小模型，所以可以自由。

**二、摘要暂不结构化；「名目清单」方案挂起。**

曾考虑让名目跟着 schema 走（`SummarySchema` + 每个字段带 hint/enum/缺省词）。既然程序不消费结构，这个方案的收益只剩"跨轮可比对"和"测试可强断言"两项，成本却是维护一份 schema 生成的清单。在库结构和筛选维度都还没定的阶段，**灵活性比可比性值钱**。

挂起不是否决。等真实用例积累出来、发现模型反复漏条件时，再拿真实数据重新论证要不要上结构——那时才知道该锁哪几个维度，而不是像现在这样从销售场景借四个格子过来。

**三、业务词一律不进 `src/`。**

这是本 ADR 里**与摘要形状无关、且现在就成立**的部分。现状违反此条：「销售额」「含税」「按城市」「上个月」写死在 `src/rewrite.py`、`src/planner.py`、`src/query_tool.py` 里。这些词换库时会变成改不动的死代码，而且会误导接手的人以为它们是有意设计。

验收标准是可执行的——改完后这条命令应输出为空：

```text
（在交接包根目录执行）
grep -rn "销售额\|含税\|按城市\|上个月\|博主\|美妆" textsql-agent/src/
```

**四、稳定性分三层。**

| 层 | 内容 | 变的时候 |
|---|---|---|
| **L1 稳定** | 两段骨架、改写问题必须可提取、名目不参与程序分支、成对落盘、管线顺序、主 Agent 决策循环（轮内可多圈）、查数工具每轮最多 1 次 | 改要写新 ADR |
| **L2 库级配置** | 类目枚举、同义词映射、Vanna 三类训练材料、问题-SQL 样例 | 改数据/配置，不改代码 |
| **L3 测试期临时值** | 假博主数据、假 SQL、搜索上限数值 | 随便改，只动 `tests/` 和 `fakes.py` |

趋势是 L3 里的东西越来越少，最终只剩测试夹具。**业务词一旦落进 `src/`，就偷偷升级成 L1 了**——这是现有代码的病根。

**五、`CONTEXT.md` 的「查询摘要」词条改成分层定义。**

原词条把四项写成了词。改为：摘要是小模型产出的自然语言说明，与「改写问题」一起产出、成对落盘，名目不参与程序分支。`CONTEXT.md` 是全仓词源锚，改词条必须配 ADR——本文即是。

---

## L1 不变量（不要动；要动先写新 ADR）

- 输出第一行必须是「改写问题：」，值是一句可独立理解的中文问句。
- 「改写问题」直接作为 B4 检索的 query。
- 摘要是一段自然语言，不写行数、不写报错、不写查询结果。
- 摘要与上次 SQL 成对落盘，只在查库成功（含 0 行）时一起覆盖；失败用尽时旧值不动、本轮摘要扔掉。
- 摘要不是主 Agent 的记忆，不经主 Agent 传入。
- 管线顺序 B3 改写 → B4 检索一次 → B5 查库对话 → B6 回填，不打乱。
- 环 A 不调查数工具、不调改写器、不调 RAG、不调查库大模型。

## 测试怎么改

唯一测试缝（一轮）不变，`run_turn` 签名不变。

**强断言点在「改写问题」**：它是程序要用的字段，必须精确断言（`result.rewritten_question == "查询美妆类目…"`）。

**摘要改弱断言**：只断言"含有关键条件"（如 `"粉丝" in result.query_summary`）。这是本决策的代价，要如实写进测试注释，不要假装它还很强。

**`tests/test_small_model_rewrite.py` 整体重写**：它的验收句是销售额示踪弹（`undesigned.md` 已如实标注），换成博主场景的示踪句。要覆盖的骨架规则不变：

- 空槽只按当前问题改写
- 有槽时把当前问题当修改（叠条件，且不丢上一轮条件）
- 本轮没有的信息不编造
- 输出没有 SQL、没有解释
- 小模型看到的 prompt 里有上次 SQL 和摘要，没有近几轮对话

**其余六个测试文件**里构造 `QuerySummary(指标=…)` 的地方，改成直接给字符串。这些测试断言的核心是主 Agent 决策循环、成对覆盖、保险丝——与摘要长什么样无关，所以是机械替换。

## 与 ADR 0001 的关系

0001 定的是「主 Agent 是一个决策循环」——一轮里想几圈，够回答才说话；改写归 B3、联网搜索不在环 B 内。本 ADR 改的是环 B 内部 B3 环节产出什么形状。两者正交。

也不能被读成"复活槽位状态机"（`spec.md` 明令禁止）。区别是：被禁的 DST 用槽位管理**多轮对话状态**；这里的摘要是**一次改写的产出**，不跨轮维护任何状态。跨轮连续性靠 `ProgramSlots` 里「上次 SQL + 摘要」成对落盘，是程序侧记录，不是会话状态机。摘要从结构化退回自然语言，更没有引入状态机——反而是往那个方向的反面走。

## 被否决的替代方案

**保持四项固定名目。** 换库即塌，且维度一多就挤爆（见背景）。

**让名目随 schema 走（前草案）。** 程序不消费结构，收益只剩可比对和可断言，成本是维护一份 schema 生成的清单。挂起，等真实用例。

**照搬 `textsql-rewrite-prompt.md` 里的完整前缀去接真小模型。** 那份前缀的规则 1–5 确实通用、要保留，但输出格式段和两处例子是销售示踪弹，要一起改。把它当"现成可用的生产提示词"会直接把销售业务词带进生产。

## 遗留（等数据库到位）

## 落地记录（2026-09-17）

12 条全部落地。`grep -rn "销售额\|含税\|按城市\|上个月\|博主\|美妆" textsql-agent/src/` 输出为空；43 个测试通过；`mypy` 无问题。

三处按实际情况偏离了本文原文，理由如下：

**一、第 6 条的「演示值放 `__main__.py`」改放 `tests/fakes.py`。** `__main__.py` 在 `src/` 里，把业务词搬过去会直接让本 ADR 第 3 条的验收命令失败——原文自相矛盾。既然验收标准是硬的，演示值就落 L3（`tests/fakes.py` 的 `SALES_CUES`）。

**二、第 7 条从「按本场景的库渲染 train」改成「演示页不再 train」。** 同上的冲突。真训练材料属于 L2（`config/` 下的 DDL 与文档），等库到位后由配置加载，不写死在 `src/` 里。演示页现在直说「查数工具未接线」，默认管线换成 `UnwiredQueryPipeline`，不再撒谎。

**三、摘要的形状从单行白名单改回「余下全部文本」。** 实现第一版把摘要收成单行、把契约外的行（含 SQL）丢掉，保留了旧测试的「drops SQL」性质。这与决策一的「自由文本」互斥：自由文本和逐行白名单不能并存。改按原文「摘要取余下文本」——标签之后的全部内容都算摘要，原样存（不折行、不动空白）。代价是「摘要里不许有 SQL / 报错 / 结果」这条 L1 不变量**只能由提示词层保证**，解析层挡不住。测试里如实标注了这一点，并补了一条断言：那句规则确实写进了喂给模型的 prompt。

顺带：`tests/test_small_model_rewrite.py` 按原文要求整体重写了，但**验收句仍是销售额示踪弹**，没有换成博主场景——真实问法要由用户给（3–10 条，见 `.scratch/textsql-agent/flow-design.md`），编一句博主问法只会重演「把编的示踪弹当成真实库结构」那次事故。等 L2 配置到位再换。

另外发现一处三值不一致，本文没动：回填截断值 `undesigned.md:95` 与现状代码是 50 行 / 约 4000 字，`.scratch/textsql-agent/flow-design.md` §4 写的是 `LIMIT 200` → 回填再截到 10 行。要哪个为准需要先拍板。

### 与本文的三处对照

**一、决策二「摘要暂不结构化」在真库上得到支持，但多了一条理由。**
原理由是「程序不消费结构」。真库上又发现一条：博主场景的筛选维度（类目 + 粉丝区间 +
邮箱非空 + 地区）比销售场景多，四项名目装不下，全挤进「过滤」那一格。
**这是背景一节预言的塌法，实测命中。**

**二、决策三的验收命令仍是硬门，但 `config/` 落在门槛之外。**
`grep` 只扫 `textsql-agent/src/`，所以 `config/` 里的业务词是允许的、也是必需的。
边界现在具体化了：**`config/` 和 `.scratch/textsql-agent/tools/` 可以有业务词，`src/` 一个都不许。**
工具脚本里的业务词应当是「从配置加载」而不是「写死」。

**三、本文的「不用改的文件」里 `sql_session.py` 只列了保险丝部分。**
实际还改了：`RowSet` 加 `matched_rows`、`ReadonlyReturn` 加 `matched_rows`、
