# 博主库的文档与口径材料

这份文本原样进查库大模型的材料（Vanna 的 documentation 那一路）。只写库里量得出来的事实，
每条后面都带数，方便复核。凡是没有数支撑的推断，下面都标了「待定」。

## 1 认人

身份键是 `xhs_id`（小红书号），470,345 行有值且零重复。

- `id` 是按粉丝降序排出来的序号，换一批数据就变，不能拿来认人。
- `nickname` 重名严重（11,623 种重名，最多的一个昵称有几十个账号），也不能当身份。
- 所以要"找出某个人"，只能靠 `xhs_id`；要"列出人"，请把 `xhs_id` 和 `nickname` 一起回填。

## 2 类目

类目真源是 `xhs_creator_category`（516,196 行，`creator_id` 对应 `xhs_creator.id`）。
`xhs_creator.raw_categories` 是它的逗号分隔副本，两边的有无完全一致（各 126,676 行无类目），
所以按类目筛用关联表更稳。

**一个账号可以有多条类目**，所以按类目筛出来的账号数加起来会大于总人数——同一人会被多个类目各算一次。
需要去重时用 `COUNT(DISTINCT creator_id)`。

**无类目的账号 126,676 个，占 26.93%。** 这些人一条类目都没有，按任何类目筛都筛不到他们，
包括"排除某类目"的写法也会把他们漏掉。要覆盖全体时不能用类目做条件。

## 3 同义词映射（口语说法 → 类目名）

用户嘴里的"美妆""宠物""美食探店"多半不是库里的 `category_name`。要按类目筛，
必须先把口语词翻成上面名单里的名字。映射表放这里：

| 口语说法 | 对应 category_name | 依据 |
|---|---|---|
| （待定） | | |

**这张表现在是空的，这是现状不是遗漏。** 里面该填什么，取决于实际问法里出现了哪些口语词；
没有真实问法就填不出来，硬填等于替用户编业务。

库里已经有一张为此准备的**空表** `dict_category_alias(category_name, alias)`（0 行），
它是这份映射在数据库里的落点。要用哪种形态（文档里的表 / 库里的表），是待定项。

一个可机械核对的做法：问一句，把问句里的每个词拿去和 114 个名字做子串匹配，
匹配不上的就是需要同义词的词。`tools/check_question.py` 干的就是这件事。

## 5 地理

- `province` 有 147 种取值，1 行为空。
- `city` 有 **105,154 行为空（22.4%）**。所以"按城市筛"和"按省份筛"会给出不同的人：
  一个人可能有省份没城市。要在城市维度做全量统计，先确认这批空值该怎么算。
- **`province` 有 2,498 行是字符串"中国"**（不是 34 个省级行政区之一）。这 2,498 行里
  城市有值的只有一部分，港澳台地区的账号全部落在这一批里。
- 因此 **按 `province LIKE '%香港%'` / `'%澳门%'` / `'%台湾%'` 筛，一律得到 0 行**。
  这是数据本身的缺口（D1），不是查询写错了。任何"香港博主"的问法现在都查不到人。

## 6 邮箱

99,544 行非空（21.16%）。两个坑：

- **含全角符号**（581 行，如全角 `＠`、全角句点），直接 `email LIKE '%@%'` 会漏。
- 空值是 `NULL` 和空串混杂，判"有没有邮箱"要同时写 `email IS NOT NULL AND TRIM(email) != ''`。

"邮箱不为空的账号共 99,544 个"（实测）。邮箱是要明文回填给用户拿去联系的信息，
但它不能进外部搜索词。
